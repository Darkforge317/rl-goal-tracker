Developer Documentation

This guide introduces the Goal Tracker codebase and the contribution workflow. For general RuneLite development rules, follow the official RuneLite Developer Guide and check the current Rejected or Rolled Back Features page before adding RuneLite-facing behavior.

Get the Project Running

  • Use Java 11, as configured by the project’s Gradle toolchain.
  • Import the repository into IntelliJ IDEA, VS Code, or another Gradle-capable IDE.
  • Run gradlew.bat test on Windows or ./gradlew test on macOS/Linux to run the unit tests.
  • Run gradlew.bat build or ./gradlew build to compile and package the plugin.

For the project’s existing RuneLite manual-launch procedure, see CONTRIBUTING.md.

How the Code Is Organized

  • GoalTrackerPlugin connects RuneLite events, cached player data, persistence, and UI refreshes.
  • GoalManager and GoalSerializer load and save goals in the player’s RuneLite configuration.
  • models contains goals, task types, task hierarchy, and undo history.
  • services contains focused operations such as task progress updates, changelog loading, panel navigation, and icons.
  • ui contains Swing panels, task forms, task interactions, and the custom changelog renderer.
  • QuestRequirements stores the prerequisite map; GoalPresetRepository defines the built-in presets.
  • src/test contains unit tests for models, services, UI behavior, and serialization.

Threading and RuneLite APIs

Read or update RuneLite client state on the client thread. Make Swing UI changes on the event dispatch thread. Keep event handlers short and avoid blocking the client thread on file or network operations.

Use supported RuneLite APIs and constants. Do not use reflection, JNI/JNA, Unsafe, runtime class loading or code generation, native serialization, or external process execution. Preserve compatibility with saved goal data when changing serialized models, and add tests for data-format changes.

Tests and Manual Verification

Add focused tests for changed behavior and run the relevant suite with the Gradle wrapper. Tests must not use Java reflection. When a change depends on live RuneLite state that unit tests cannot cover, document specific manual verification steps for a plugin maintainer to run in RuneLite.

Pull Requests and Changelogs

Keep pull requests focused and explain the behavior changed and how it was verified. For changelog-worthy work, add an entry to the next-release changelog in the same pull request. The changelog guide explains the release sections and image rules. Do not bump the plugin version; the plugin owner does that when preparing a release.

The repository’s AGENTS.md has additional contributor and repository guidance.

Working on This Documentation

The site is built from HTML pages in docs/ using Jekyll and the shared layout in docs/_layouts/default.html. Keep the YAML frontmatter on every page, including show_coming_soon_page. Set the flag to false to display the page body or true to show the shared Coming Soon section instead. This lets a page be hidden without removing its content.

To build the site locally, open a terminal in docs/, install the bundled gems with bundle install if needed, then run bundle exec jekyll build. The generated site is written to docs/_site/.
